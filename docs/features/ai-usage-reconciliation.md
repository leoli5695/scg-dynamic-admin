# AI 用量核对与补偿

Token 计量页可勾选「仅显示待核对明细」，筛选用量 `UNKNOWN` / `ESTIMATED` 或结算 `PENDING` / `FAILED` 的记录。「核对记录」打开该请求的处理页面。登录用户可查看处理结果，只有 `ADMIN` 可以提交或重试。

## 核实与提交

管理员核实供应商账单、请求追踪、原始配额结算和本地降级待回补记录后，填写：

- 确认的输入、输出、总 Token，及应计费 Token。总 Token 必须等于输入加输出。
- 月额度、日额度各自的调整量：正数补扣已用额度，负数退款，0 表示已核实该桶无需调整。不能直接拿「实际减预扣」同时应用到两个桶，因为旧结算有可能只完成其中一个桶。
- 核实依据与处理说明。提交前会再次展示两项调整量，提交后金额固定。

每条用量最多关联一笔不可变更的补偿单。同一内容重复提交返回已有单据；修改内容再次提交返回冲突。页面保留处理人、依据、调整量、原始用量快照、执行次数和最近错误。原始采集事件的历史信息在快照中保留，核对完成后的计量明细与统计使用核实后的 Token，并标记 `RECONCILED / APPLIED`。

## 失败恢复

补偿单先在数据库提交为 `PENDING`，然后再执行 Redis 调整。Redis Lua 同时检查两个桶，并以固定补偿 ID 保存执行回执。Redis 已执行但响应丢失、或随后数据库更新失败时，重试会复用同一 ID，不重复执行增减。

`PENDING` 单据每 30 秒自动重试一次，每轮最多 32 笔，也可点击「重试此笔补偿」。自动重试只执行管理员已核实并提交的操作，不会自动估计未知用量。`gateway.token-usage.reconciliation-retry-ms` 可调整重试间隔。

缺少原始周期或周期额度未启用时，只能以两个调整量均为 0 核对用量。非零调整只能作用于网关记录的原始周期。Redis 桶已过期、缺失、数据无效或退款后将低于 0 时，整笔调整不会写入，单据转为 `REVIEW_REQUIRED`，需人工复核后手动重试。系统不会重新创建已过期的额度桶。

两个调整量均为 0 时，仅在数据库中完成用量核对，不访问 Redis。补偿不会改动窗口速率限制计数。

## 部署与边界

1. 在前两份用量迁移已完成的基础上，先执行 `gateway-admin/src/main/resources/sql/alter-token-usage-reconciliation.sql`。
2. 先升级管理端，再升级网关。新网关上报 `quotaMonth`、`quotaDay`、`quotaPeriod`，记录请求原始周期和额度范围；历史记录不会倒推补填。
3. 本功能沿用现有配额的 Redis 实例及键格式。当前多键 Lua 不支持跨槽的 Redis Cluster 部署。
4. Redis 的 `token_quota:reconciliation:<补偿ID>` 回执不设置过期时间，避免长时间未确认的操作被重复执行。存在待处理单据时不能清理回执；Redis 持久性也决定回执在服务器故障后的保留能力。

本阶段提供管理员核实后的用量修正、配额补偿和安全重试。供应商账单自动拉取、旧版结算部分成功的自动判定、本地降级额度的自动审计仍未接入，处理人必须先完成这些核实。数据库与 Redis 不构成分布式事务；恢复依赖已提交的操作意图及 Redis 执行回执。
