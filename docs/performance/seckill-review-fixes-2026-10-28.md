# 秒杀链路优化与可靠性修复（2026-10-28）

后续状态、身份与 Redis 降级策略变更见 [状态与身份边界修复](seckill-state-security-fixes-2026-10-28.md)，其中的停售与持久化回补策略覆盖本页涉及的旧降级行为。

## 订单确认与事务回查

订单消费者现在等待数据库批次写入完成，再持久化 ES 同步/延迟回补事件，二者都确认后才正常返回。数据库失败、容量耗尽、等待超时或事件入库失败均抛异常，交由 RocketMQ 重试。删除了“processing 锁存在即直接确认”的路径，避免把未落库的在途消息误认为已经处理。

重投首先按 user_id + order_no 查数据库；订单已存在也继续补齐待发送事件和事务状态，不因为已有订单而跳过后续恢复。订单写入与事件入库不是一个跨库原子事务：中途宕机依靠尚未确认的 MQ 消息重投收敛。数据库唯一索引兜底并发重投；重复键导致的批次失败会交还 MQ，不立即逐条重试压垮数据库。需持续监控 MQ 重试、死信和订单处理延迟，不能把它理解为无限期、无运维介入的投递保证。

事务回查的 PROCESSING 表示生产端事务日志已持久化、下游订单尚未完成，足以返回 COMMIT_MESSAGE。下游 SUCCESS 不再作为消息可见的前提。数据库读取异常返回 UNKNOW。回查取消了会跨实例陈旧的本地状态缓存，直接走 transaction_id 唯一索引。发送确认丢失时先查询已提交日志，已有有效日志不重复执行本地降级事务，也不释放其库存；数据库不可读、结果未知时保留库存等待核对，不能冒险回补。

## 批量写入与背压

订单按实际库表位置归组，不再按完整 user_id 拆组。同一库表的不同用户可以进入同一条批量 INSERT。正常路径在同一刷新流程中批量更新事务状态，不再每条执行 SELECT + UPDATE；取消无界的异步状态更新线程池。

queue-capacity 默认 200，包含排队和正在写入的订单。一次只允许一个刷新流程，超时等待不会提前释放在途额度；没有额外堆积的刷新任务。acknowledgement-timeout-ms 默认 5000，约束 Future 等待时间，不是 JDBC 语句取消承诺；数据库连接/查询超时仍需单独配置。停止准入后，停机先等待当前写入，再刷新剩余队列。

订单消费限流改为单次 tryAcquire，取消每条消息最多十次 Redis 重试和 sleep。订单消费、延迟回补消费与超时事务补偿的订单查询都带 user_id，避免这些已有用户信息的路径广播到 128 张表。未携带用户的订单查询/支付接口仍有历史全路由行为，本轮没有假装订单号唯一索引能够自动路由。

## 后续事件投递

新增 ds_0.order_delivery，一条记录保存原消息、ES/延迟回补的独立确认位、重试次数和下次执行时间。重复入库不会覆盖原内容。独立单线程每次最多读取 50 条，确认 SEND_OK 后才标记对应部分，失败指数退避至最多 60 秒；仅两个固定周期任务，没有随请求增长的内存发送任务队列，也不会占用订单刷批使用的共享调度线程。多个实例可能并发投递同一事件，发送成功后进程也可能在标记前宕机，因此语义是至少一次，接收方仍须幂等。

发送完成记录保留七天；未完成记录不自动删除。延迟消息从实际发送时开始计时，事件积压会推迟其触发，原有二十分钟未支付订单扫描仍需保留。数据库积压必须监控，不能靠删除未发送记录缓解。

```sql
SELECT COUNT(*) AS pending, MIN(created_at) AS oldest,
       MAX(attempts) AS max_attempts
FROM seckill_db_0.order_delivery WHERE completed = 0;
```

## 订单路由 v2（需离线迁移后切换）

默认保留 v1：库 user_id % 8，表 user_id % 16，避免现有数据突然查不到。v2 保持库不变，表改为 (user_id DIV 8) % 16；128 个连续用户覆盖全部 8 × 16 个位置，Java 批次归组与运行时 Groovy 表达式已验证一致。

生成迁移 SQL（只生成，不连接数据库）：

```powershell
node seckill-core-engine/scripts/plan-order-routing-v2.mjs D:/migration/order-routing-v2.sql
```

必须先备份、停止全部应用写入/消费者/定时任务并处理完在途订单。生成的 SQL 建立新表，复制所有列及主键，校验库归属与数量，再用一次 RENAME 切换；原表保留为 order_v1_backup_*。有重复主键、结构差异或任何 SQL 错误都必须中止，禁止 mysql --force、INSERT IGNORE 或直接删除冲突行。脚本适用于当前同一 MySQL 服务器的八库结构；多个 MySQL 主机需要逐主机迁移和协调切换。保持停机，全部实例设置 SECKILL_ORDER_ROUTING_VERSION=2、核对实际路由后再恢复流量。

迁移前可保持 v1 回滚代码；迁移后恢复旧路由必须先停写并将新增数据反向迁移，不能只翻开关。备份表不应在验收前清理。

## Redis Key 格式与容量边界

stock-hash-tag-enabled 默认 false，兼容已有 Key。启用后，一个活动的库存、购买集合和分片记录统一包含 {activityId}，脚本调用显式传入每个库存 Key。预热、扣减、批量扣减、同步、回补、支付/退款库存 Key、清理和对账保持同一格式。配置原生 Redis Cluster 却使用旧格式时，启动检查会拒绝运行。

查看迁移计划（无 Redis 连接或写入）：

```powershell
node seckill-core-engine/scripts/migrate-stock-hash-tags.mjs 42 8
```

离线复制模式增加 --copy-offline，使用 redis-cli 的 DUMP/RESTORE 保留值与过期时间，逐 Key 验证，保留原 Key，不覆盖不同的目标数据；主机/端口使用 REDIS_HOST、REDIS_PORT，认证使用 REDISCLI_AUTH。必须停止所有库存写入、完成在途回补，并枚举全部仍可能被订单/退款引用的活动。全部实例一起切换 SECKILL_STOCK_HASH_TAG_ENABLED=true 后再恢复。新旧格式是两个独立库存池，绝不能滚动混用；复制工具不负责自动停流或协调切换。真实复制模式尚未在本轮环境执行，必须先在恢复出的测试数据上演练。

同一活动依然是一个原子槽，多库存 Key 不代表跨节点分流或吞吐乘八。独立库存桶涉及跨桶防重、预占与回补协议，本轮没有改变“一用户一活动”的原子语义，也不宣称单活动可线性扩容。

## 库存异常路径

商品存在、所属活动、价格和数量在预占前校验。只有本次请求确实扣减成功，普通异常路径才回补；内部发送方法不再重复回补。Lua 同时拒绝零/负数及非整数数量。Redis/MQ 结果未知不能等同明确失败，保留库存并依赖对账和人工核对，不能保证所有故障下自动恢复。

1. 先执行 src/main/resources/sql/order-delivery-migration.sql（新增表，旧订单不变）；关闭分库分表的部署应在其实际默认数据库创建同名表。
2. 更新秒杀服务，暂时保持订单路由 v1 与旧 Redis 格式，验证订单确认、消息重试、事件积压和未支付补偿。
3. 路由 v2、Redis hash tag 是独立的维护窗口操作，分别演练迁移再切换，不能直接开启开关。
