# 网关压测问题修复与验证（2026-10-28）

## 追踪上报

- 普通和异常追踪统一进入 `TraceReportDispatcher`，不再每请求发起独立异步上报，也不再使用公共线程池。队列最多 256 条、总计 4 MiB，单条最多 256 KiB；额度包含正在发送的批次。
- 专用连接池最多一个连接，每批最多 16 条追踪；每次 HTTP 发送截止时间 2 秒。发送失败不自动重试，以免在管理端故障时扩大请求量。
- 过滤器执行记录也批量上报，管理端先进入有界异步队列（最多 256 批、4 MiB），不会让 HTTP 接收线程等待数据库。追踪入库缓冲增加 16 MiB 总量上限，同一时间只有一个落库任务，取消逐条重试放大。
- 两类数据均改为 `JdbcTemplate.batchUpdate`，不再让 IDENTITY 主键把 `saveAll` 变成逐行插入；MySQL URL 开启 `rewriteBatchedStatements=true`。追踪每批最多 200 条且估算正文不超过 1 MiB；过滤器后台会合并小批次，每次最多 2048 行、1 MiB 编码输入。使用事务保证失败回滚，并显式填充原来由 JPA `@PrePersist` 提供的时间字段。覆盖数据源 URL 的部署也应保留批量重写选项。
- 队列饱和时诊断数据可能丢失，业务请求不等待诊断落库。网关的 `gateway_trace_export_dropped_total`、`gateway_trace_export_failed_total`、`gateway_trace_export_queued_bytes` 以及管理端的 `gateway_admin_filter_executions_*` 指标可观察丢弃和积压。追踪接收统计提供 `queuedBytes`。
- 管理端兼容结构化对象和 JSON 字符串类型的追踪字段，并保存响应头、响应体，避免 `LinkedHashMap` 强转 `String` 导致 400。

## JWT 与连接故障

- 同一 Token 的并发撤销查询共享一个进行中的任务；控制开关查询也合并。最多保留 512 个进行中的任务。
- `gateway.jwt.revocation.timeout-ms` 默认 500 ms，限制整次查询时间，避免开关查询与黑名单查询各自等待数秒。
- 已配置 Redis 时，查询失败、超时或任务额度耗尽返回 **503**，不再将查询失败当作“未撤销”。失败后短暂快速拒绝 1 秒，减少断连期间的 Redis 请求堆积。
- 保留原本 5 秒的本地撤销判定缓存；不因 Redis 故障延长旧判定。仍支持明确关闭撤销检查，以及未配置 Redis 的可选部署模式。
- 清理本地撤销缓存时增加代际标识，缓存写回与失效共用短锁，保证检查代际和写入是原子的，避免清理前启动的慢查询在完成后重新写入旧结果。最终同步保护追加的认证回归与打包通过。
- 本地依赖隧道增加后台监护和退避重连，Redis 与 Nacos 使用独立 SSH 连接，配置位于 Git 忽略目录 `.local-runtime/watch-tunnel.ps1`。停止监护应使用对应的 `stop-redis-tunnel` / `stop-infra-tunnel` / `stop-db-tunnel` 标记，单独结束 SSH 子进程会自动重连。生产服务器间直接连接依赖，不需要这套本地隧道。
- 本地经公网连接依赖，实测 Redis PING 有几十到几百毫秒波动，重连初期曾达 4 秒。因此本机将总查询时限设为 1000 ms；默认代码时限仍为可配置的 500 ms，具体部署需按实际链路延迟设置。

## 大请求体

- 静态服务只有一个后端，或没有其他可重试后端时，直接转发请求流，不再完整聚合请求体。
- 重试正文缓存阈值从 1 MiB 降为 64 KiB，并增加 16 MiB 并发预算。超限和未知长度上传直接转发，停用本次实例切换重试；不会为诊断/重试缓存而中途截断上传。需要正文完整校验的 HMAC、WAF 等逻辑仍执行自身限制。
- 小请求保留原有重放重试能力；缓存额度在完成、异常和取消时释放。
- 追踪正文只复制剩余前缀，保持网络缓冲区原始读取位置，收到完整前缀后再解码 UTF-8，避免大响应分块的多余复制和多字节字符被逐块破坏。

## 实际服务验证

保持 512 MiB 堆、256 MiB 直接内存上限及 ActiveProcessorCount=4；上游与压力端均在本机，远程依赖仍位于 139。各阶段为同机观测，存在压力端、主机内存与网络波动，不能作为网关容量上限，也不是严格隔离的性能 A/B。

| 1 MiB 上传，2 轮，每轮 8 秒 | 128 | 389–675 | 1052 ms | 162 MiB |

四轮大包请求和两个追踪场景均未出现业务响应/正文校验失败。此前大包对应堆峰达到 424–503 MiB，但堆峰含待回收垃圾，不能据此计算保留内存或宣称排除了内存泄漏。流式转发与小包重放均有独立回归验证。

1% 阶段管理端接收的 826 条请求追踪最终全部落库，服务端丢弃为 0，队列排空。该阶段客户端仍有 102 条报告未确认完整上报，过滤器细节与请求追踪是两条独立上报，不能由“追踪落库”推导所有细节也已保存。导出时限随后放宽至 2 秒，最终过滤器队列数量上限增至 256，但内存上限仍为 4 MiB，以容纳小批次启动抖动。

100% 过载阶段网关报告丢弃 75925 条诊断、3552 条未确认完整导出；这是有界背压的可观察结果，并非 100% 追踪完整保存的承诺。管理端累计接收的 5385 条请求追踪全部落库且排空；其中包括前面的 826 条。测量窗口没有上报连接池排满、追踪 400 或心跳失败，实例保持 Running、missedHeartbeats=0。

人工中断 Redis 隧道后，新签发的、未命中本地缓存的 JWT 从正常 200 变为 503，耗时约 1009.7 ms；恢复隧道后重新使用新 Token，返回 200，耗时约 154.4 ms。自动重启 SSH 子进程也已验证。

远程依赖/本机调度仍存在延迟尖峰：拆分连接并使用 1 秒总时限后的四轮 JWT 测试中，有一轮产生 2208 个 503，其余三轮为 0。这些请求已安全拒绝，不能写成“认证失败为零”或“公网链路抖动已消除”。本次修复解决排队放大、查询风暴与故障时放行，无法消除物理链路和主机负载问题。
